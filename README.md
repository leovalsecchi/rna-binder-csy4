# De novo protein binders to the Csy4 crRNA hairpin — pipeline archive

Code archive for the computational arm of the thesis *De novo design of RNA-binding
proteins targeting the Csy4 crRNA hairpin*: five generative design stacks, three
structure re-prediction backends, the metric suite computed over them, and the filter
cascade that reduced 6,992,515 designs to the 12,000-member library that went to
synthesis.

This is an **as-run snapshot**, not a reconstructed history. The pipeline was developed
directly on a cluster filesystem without version control, so there is no commit series
to publish; the snapshot was taken from the production tree at the computational data
freeze and tagged once. What is here is what ran.

## What this archive can and cannot do

It documents the pipeline exactly: every configuration file is the production file, not
a reconstruction. Campaign submission overrode **only** scheduler fields
(partition, nodelist, GRES, walltime) plus the per-job HalluDesign seed, so
`configs/*/default.yaml` can be cited directly as the parameter set that ran.

It will **not** regenerate the dataset, and no amount of care with this code would
make it do so:

- **RFdiffusion3** runs with `seed: null` — unset.
- **BoltzGen** and **BoltzDesign1** expose no seed argument at all.
- **LigandMPNN** is pinned at a constant `seed: 42` across all four stacks that use it,
  so within one backbone the ten sampled sequences are fixed, but the backbone handed
  to it is not.
- **HalluDesign** is seeded per job, and its initial 80-mer is reproducible from that
  seed, but its vendored LigandMPNN wrapper draws a fresh seed from OS entropy and
  overwrites the global torch/numpy/random state before sequence sampling
  (`halludesign_upgrade/LigandMPNN/package.py`). Everything after that point diverges
  between runs.

**No stack in this work is seed-reproducible at the level of an individual design.**
Aggregate distributions are reproducible; individual designs are not. Where a specific
design matters, use the archived coordinates rather than attempting to regenerate it.

## Layout

```
pipeline/src/        rna_binder package: pipelines, io, filters, analysis, refolders
pipeline/scripts/    collection, cleaning, metric computation, aggregation, selection
pipeline/pylibs/     helper libraries imported by the above
targets/             the Csy4 target itself: 4AL5-derived coordinates, the 16-nt MSA
                     as run, AF3/Protenix templates, hotspot file (empty -- see below)
configs/             production YAML for all five stacks and three refold backends
ops/                 Slurm submission, refold drivers, watchers, aggregation, loops
analysis/            plotting suite, campaign kit
figures/             the figure and supplementary-table code: one directory per
                     panel, plus the shared style module (see figures/README.md)
patches/             modifications applied to third-party tools (see below)
docs/                design and findings notes cited by the Methods chapter
provenance/          software and container versions, deviation timeline, the gate as
                     JSON, container deffiles, environment manifests, build script
```

Two directories deliberately absent:

- `code/envs/` (~724k lines) — the pip environment. Pinned by version in
  `provenance/versions.tsv` instead.
- `code/pylibs_dockq/` (~599k lines) — vendored DockQ 2.1.3. Pinned by version and
  dependency set; the upstream release is public.

`.bak_pre_*` files are kept on purpose. Several are the only surviving record of
pre-fix behaviour for the changes listed in `provenance/deviations.md`, and designs
produced before those dates were generated by the `.bak` variant, not the live file.

## Patches to third-party tools

Three of the five stacks did not run as distributed. The patches under `patches/` are
part of the method, not packaging detail — results are not comparable to upstream
behaviour without them. See `provenance/deviations.md` for what each one changes and
which designs it affects.

## Containers

Model execution was containerised (`apptainer exec --nv`). Images are 3.5–15.7 GB and
are neither in this repository nor deposited: together they are about 60 GB, and several
carry model weights that may not be redistributed. They are cited by sha256 digest in
`provenance/software_versions.md`. All nine production images have been hashed.

`provenance/container_recipes/` holds the Apptainer definition file for all nine, plus
the Dockerfile recovered from inside `boltz_design1.sif`. Be aware what those deffiles
are worth: only `foundry_0.1.9.def` has real build steps, and even that one records just
an hbplus overlay applied to an earlier copy of the same image. The other eight are
two-line pointers at a source. Two of those sources are citable registry references
(LigandMPNN, AlphaFold3); four name a local Docker daemon tag (`boltzgen:latest`,
`boltz_design1:latest`, `boltz2:latest`, `pyrosetta:latest`) which cannot be resolved
after the fact; `esmc.sif` points at a `docker-archive` tar that was deleted; and
`af3_protenix_esm.sif` points at a sandbox directory that no longer exists.

So no image here is rebuildable from its recipe. The digest is the identifier that
matters, and the images themselves are the artefact — held on institutional storage,
not deposited. Anyone needing a byte-exact environment should ask for them.

Two components additionally have no recoverable version string at all: the Protenix
distribution inside `af3_protenix_esm.sif`, and `esmc.sif` beyond its package list.

## The filter gate

`provenance/gate_v6_final.json` is the filter that defines the gated set, lifted
verbatim from the header of the export that produced it (`n=55706`,
`store_n=6992515`). It is recorded as data rather than described in prose because the
selection code can express gates that were never run: evaluating the filter module's
defaults gives roughly 66,000 designs, not 55,706. The JSON is what ran.

In words, all four conditions ANDed: self-consistency RMSD ≤ 3 Å in *either* backend;
DockQ ≥ 0.7 in *either* backend; longest single-residue run ≤ 5; hairpin-foot clearance
`footnb_010` ≤ 5 in *both* backends; and ipTM (max across backends) ≥ 0.6. "Either
backend" means AlphaFold3 or ESMFold2 — Boltz-2 is not in the gate.

## Where to start

The generation layer cannot be reproduced design-by-design, for the reasons above. The
**analysis layer is deterministic given structures**, and that is the part worth
re-running. The four stages below are the whole pipeline; everything else in this tree
is support for them.

**1. Generation and re-prediction** — `pipeline/scripts/launch.py <config> --label <name>
--num-runs <N>`, with the production YAML in `configs/`: one directory per route
(`rfd3`, `boltzgen`, `boltzdesign`, `halludesign`, each with its `__multif` variant) and
one per re-prediction backend (`refold__af3`, `refold__b2`, `refold__esm`). Slurm
submission, the refold drivers and the watchers that kept them alive are in `ops/`.
Needs the cluster, the containers in `provenance/software_versions.md` and the weights named there.

**2. Collection and metrics** — the re-runnable part:

```bash
bash pipeline/scripts/run_analysis.sh <name> <run_dir> [<run_dir> ...]
python3 pipeline/scripts/compute_metrics.py --dir analyses/<name> --full
```

`run_analysis.sh` drives `collect.py` (one row per design with its AF3-msaoff, Boltz-2
and ESMFold2 re-prediction metrics) into `clean.py` (filters the raw collection, draws a
per-stack sample) into `compute_metrics.py` (appends the structural, RNA-contact and
H-bond columns), writing `analyses/<name>/`: `collected_raw.csv`, `collected_clean.csv`,
`sample10k.csv`, `sample10k_metrics.csv`. The second command runs the metric pass over
the full set rather than the sample. `aggregate_metrics.py` merges several runs into one
table. Input is run directories holding the design and re-prediction CIFs; those are not
in this repository — see `provenance/data_availability.md`.

**3. The gate** — the filter that took 6,992,515 designs to the 55,706 that passed is
frozen as `provenance/gate_v6_final.json` (`filter.tiers`, `filter.combine`,
`filter.iptm`), lifted from the header of the export that produced the set.
`analysis/binder_filter/` applies it: `store.py` loads the columnar store (one `.npy` per
column), `filters.py` evaluates the spec, `export.py` writes the passing set as a CSV
whose header carries the exact filter that produced it, and `app.py` is the interactive
bench the thresholds were chosen on. Read that directory's README before trusting a
consensus column: Boltz-2 is deliberately excluded from the filter, and the bare
`consensus_*` columns in the master do fold it in.

**4. Maps, selection and plots** — `analysis/binder_map/` builds the fold and epitope
axes with Foldseek and does the clustering behind the library selection;
`analysis/binder_filter/build_library_map.py` produces the ordered library;
`analysis/plots_tools/` is the plotting suite. `analysis/campaign_kit/`,
`analysis/metric_explorer/` and `analysis/rna_binder_gui/` are the operational tools the
campaign was driven and inspected with, each with its own README.

### Environment

There is no `requirements.txt` by design: exact versions are in
`provenance/versions.tsv`, the resolved environments in `provenance/env_manifests.md`,
and the containers in `provenance/software_versions.md`, cited by sha256 digest.

### One path caveat

Usage lines inside the scripts (131 files) were written for the production tree, where
the pipeline lived under `code/scripts/`. In this archive those files are
`pipeline/scripts/`; the rest of the path is unchanged. Nothing reads those strings —
they are comments and help text.

### Rebuilding this archive

`provenance/build_archive.sh` refreshes this tree from the production source. It is the
script that produced the repository, not one a reader needs.
